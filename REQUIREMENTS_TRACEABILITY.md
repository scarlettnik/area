# Проверка актуальной модели ЛЦТ 2026

Основа: `.survey/corrected-network-optimizer/sources/technical-appendix.txt` и
`clarifications.txt` из `main`. Этот файл фиксирует требования, которые должны
оставаться инвариантами solver и независимого validator.

## Вход и геометрия

- Один GeoJSON FeatureCollection в WGS84; все метры/длины/габариты — EPSG:32637.
- ID остаются строковыми/числовыми и не интерпретируются по формату.
- Одна новая LineString означает пару подающего/обратного трубопроводов; расход не удваивается.
- Для каждой подключенной точки существует ровно один путь до места присоединения; циклы запрещены.
- Новые линии не пересекаются вне общего узла.
- Повороты не более 90°. Необоснованные мелкие изломы/ступеньки удаляются refinement; отдельной цены поворота нет.

## ОКС

- `restriction_type=oks` непроходим, с отступом 5/7/9 м по ДУ плюс половина габарита пары.
- Для собственного ОКС разрешен один финальный прямой ввод через ближайшую границу; остальные ограничения продолжают действовать.
- Каждая `oks_connection_point` — самостоятельная цель.
- Нельзя намеренно оставить технически доступную точку неподключенной ради score: поиск coverage-first.

## Топология, ДУ, камеры

- Расход участка = сумма downstream `flow_tph`.
- ДУ — минимальный, удовлетворяющий одновременно расходу и предельной непрерывной длине; произвольное завышение запрещено.
- По направлению к существующей сети ДУ не уменьшается.
- Камера/technical_node без смены ДУ не обнуляет счетчик предельной длины.
- Разветвления только в `heat_chamber`; максимум 4 примыкающих линейных участка с учетом существующей сети.
- Обычный поворот отдельного узла не требует; `technical_node` — только смена параметра без разветвления.
- Если присоединение <=10 м от существующей камеры и degree после подключения <=4 — используется она; иначе новая камера на существующей линии.
- Новая камера включает стоимость присоединения; к существующей камере каждая новая входящая линия = отдельная врезка 5 млн.
- Реконструкция существующей сети в актуальной модели не выполняется.

## Ограничения и специальные проходы

- park/social_area/prohibited_site/water/railway — непроходимы с нормативным отступом.
- road/tram — special, прямой проход, угол >=45°, по 3 м за полигоном; K=1.60/1.75.
- gas/power/existing heat — special; горизонтальные отступы 2/2/1 м при проходе рядом, окно пересечения ±2 м; K=1.25/1.15/1.05.
- Внутри разрешенного special-crossing горизонтальный отступ не применяется; вне окна применяется.
- При наложении special-зон берется max(K), а не сумма/произведение.
- 2D не применяет вертикальные требования; depth применяет min depth 0.7, normal 3.0, slope <=0.10 и профиль пересечений.

## Экспорт и проверка

- Выходные типы: `heat_network`, `heat_chamber`, `technical_node`, `variant_summary`; отдельного `tie_in` нет.
- Endpoints LineString совпадают с объектами `start_node_id`/`end_node_id`.
- Rank строго по official score среди экспортируемых вариантов.
- Финальный GeoJSON обязательно сериализуется и заново читается независимым `validate_routing.py`.
- Hardened orchestrator отбрасывает finalist, если round-trip validator его не принимает, и пробует исходный не-refined вариант.

## Оптимальность

Solver — эвристический visibility + Beam/ALNS. Полный глобальный минимум на непрерывной геометрии не доказан.
`run_portfolio.py` уменьшает зависимость от одного random seed; выбирается максимальное покрытие, затем минимальный официальный score среди независимо валидных запусков.
